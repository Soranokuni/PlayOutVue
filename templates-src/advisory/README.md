# CG advisory template — source

The on-air CasparCG template and the CG Studio workstation are one document:
`public/templates/playout/advisory.html`, with a byte-identical twin at
`src/assets/templates/playout/advisory.html`. CasparCG needs a single
self-contained HTML file plus `vendor/` and `fonts/`, so those two copies are
**build output**. This directory is the source.

```
npm run build:cg                        # write both copies
node scripts/build-advisory.mjs --check # fail if they are stale (CI)
```

`predev` and `prebuild` run the build, and `src/lib/__tests__/advisoryBuild.test.ts`
fails if a committed copy differs from what the sources produce. Editing the
generated files by hand works right up until the next build reverts it.

## Layout

| Part | What is in it |
|---|---|
| `index.html` | The skeleton: head, body markup, and the three `/* @… */` markers the build splices into |
| `mode.js` | Mode detection, which runs before first paint so transparency is never late |
| `css/fonts.css` | `@font-face` for the vendored faces in `public/templates/playout/fonts/` |
| `css/onair-*.css` | Tokens, the two broadcast stages, and the on-air override block |
| `css/studio-*.css` | Workstation chrome only: shell, cards, console, widgets |
| `core/*.js` | Things transmission needs: assets, theme tables, text, render, timeline, subtitle, and the `window.update`/`play`/`stop` contract |
| `studio/*.js` | Things only the operator's browser needs: canvas drag, console, boot, presets, tags, dialogs |

## Two things to know before moving code

**The concatenation order is the file.** `CSS_PARTS` and `JS_PARTS` in
`scripts/build-advisory.mjs` are cascade order and evaluation order
respectively. Everything lands in one classic `<script>` scope, so function
declarations hoist between parts but top-level `let`/`const` do not: a part
that declares a table must come before any part that reads it at evaluation
time.

**The split is a cut, not a re-layering.** These parts were sliced out of the
single file in source order so the build reproduces it byte-for-byte, which is
what makes the split verifiable. Several `core/` parts still contain
studio-only functions and vice versa; the file names say which side each part
mostly serves, not which side every line in it serves. Separating them means
moving code, and that belongs with the schema refactor that rewrites these
functions anyway — not with the cut.

## The one line you cannot reshape

`let BAKED_DEFAULT_PRESET = {…};` is generated by the build from
`public/templates/playout/advisory_default_preset.json` (keys sorted), so the
sidecar and the baked constant cannot drift. The Rust studio bridge finds that
line by string anchor when it bakes a deployed preset into the template
(`src-tauri/src/studio_server.rs`). Change the declaration's shape and Save &
Deploy stops working without saying so.

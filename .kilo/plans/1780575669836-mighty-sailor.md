# DeckLink Output Wizard & Production Readiness Audit

## Overview
Build a hidden wizard (behind gear button → Settings → "DeckLink Output Wizard") that guides operators through configuring CasparCG DeckLink output and live-rebroadcast input. Simultaneously audit the application for production-grade stability, efficiency, and SOTA readiness.

---

## Phase 1: DeckLink Output Wizard

### 1.1 New Component: `src/components/DeckLinkWizard.vue`
**Purpose**: A 5-step modal wizard with guided DeckLink setup for CasparCG.

**Step Flow**:
| Step | Title | UI | Logic |
|---|---|---|---|
| 1 | **Load Configuration** | File path display, "Load Config" button, auto-detect button. Displays read-only summary of current channel and DeckLink consumers | Calls `load_caspar_config` via `invoke`, parses DeckLink from channel consumers. Shorthand: reads `settings.casparConfigPath` then loads |
| 2 | **Program Output (SDI)** | Dropdown: DeckLink device # (1–8), optional key device, embedded audio toggle, buffer depth (1–7), latency (normal/low/default). Radio: keyer mode | Maps to `<decklink>` consumer on **channel 1**. Shows current state if already configured |
| 3 | **Live Input (SDI)** | Dropdown: DeckLink device # (1–8) for ingest. "Enable live rebroadcast" toggle. Shows how input will route to output (device X → channel 1 → output Y) | Sets up the `liveInputSourceName` in settings. For Caspar, this corresponds to `decklink://device/<N>` which gets played via AMCP `PLAY 1-20 decklink://device/<N>` |
| 4 | **Video Standard** | Radio group: 1080i5000 (PAL), 1080p2500, 1080p3000, 720p5000. Shows current config. Warning if mismatched with playout profile | Sets `<channel><video-mode>` in config. Must align with `settings.playoutProfile` |
| 5 | **Review & Apply** | Full summary card showing all changes. "Test Connectivity" button (sends AMCP `INFO` to verify CasparCG is alive). "Apply & Save" button. "Backup Current Config" button | Writes to `casparcg.config` via `save_caspar_config_structured`. Updates `settings.decklinkOutputName` and `settings.liveInputSourceName`. Sends AMCP `ADD 1 DECKLINK <N>` to activate. Backup copies config to `.bak` |

**Validation rules**:
- Output device != Input device (if live rebroadcast is enabled)
- Device numbers must be 1–8 (Blackmagic DeckLink quad-card range)
- Video mode must match a supported CasparCG format string
- Channel must have consumers (at least one DeckLink output)
- CasparCG server must be reachable on `127.0.0.1:5250` before applying
- Config path must exist and be writable

**Safety features**:
1. **Backup before write**: Creates `<config>.bak` with timestamp
2. **Rollback on failure**: If AMCP test fails after apply, offer to revert
3. **Dry-run preview**: Shows AMCP commands that will be executed
4. **Validation gate**: Cannot proceed to next step if current step has errors
5. **Confirmation dialog**: "This will rewrite your CasparCG configuration. Continue?"

### 1.2 New Rust Command: `apply_decklink_wizard_config`

**Location**: `src-tauri/src/caspar_config.rs` (or new `src-tauri/src/decklink_wizard.rs`)

```rust
#[tauri::command]
async fn apply_decklink_wizard_config(
    config_path: String,
    channel_index: usize,
    output_device: u32,
    input_device: Option<u32>,
    video_mode: String,
    embedded_audio: bool,
    buffer_depth: i32,
    latency: String,
    key_device: Option<i32>,
) -> Result<ApplyResult, String>
```

**Logic**:
1. Load current config from `config_path`
2. Ensure channel at `channel_index` exists (create if needed)
3. Set `video_mode` on the channel
4. Add/replace DeckLink consumer with specified device, key, audio, buffer, latency
5. Serialize back to XML, validate with `from_str`, write to disk
6. Return the new raw XML + confirmation of changes

## Phase 2: Production Stability Audit

### 2.1 `caspar.ts` — Connection & Reconnection Review

**Issues found**:
1. **Reconnect attempts** (`src/services/caspar.ts:519-549`): Hardcoded 4 foreground attempts / 1 background attempt. Should be configurable or at least increased to 6 foreground. In production, brief network glitches should not require manual reconnect.
2. **Timeout values**: `RECONNECT_BASE_DELAY_MS = 750`, `RECONNECT_MAX_DELAY_MS = 15000`. Good for LAN, but on congested broadcast networks, add jitter (±100ms) to prevent thundering-herd.
3. **No heartbeat**: After connection, no periodic health check. If CasparCG silently crashes, the app doesn't notice until next command. Add 5-second heartbeat via `INFO` command.
4. **`sendRawCommand` error handling** (`caspar.ts:565-578`): Immediately marks disconnected on any error. Some AMCP errors (e.g., file not found) are not connection failures. Refine: only mark disconnected on I/O errors (timeout, ECONNRESET, etc.).

**Recommended fixes**:
- Add heartbeat interval (5s) that pings `INFO` when connected
- Distinguish transport errors from application errors in `sendRawCommand`
- Increase foreground reconnect attempts to 6
- Add reconnect jitter

### 2.2 `caspar.ts` — DeckLink Commands Review

**Current implementation** (`caspar.ts:835-847`):

```ts
async startDeckLink(outputName: string) {
    const deviceMatch = outputName.match(/\d+/);
    const deviceId = deviceMatch ? deviceMatch[0] : '1';
    await sendRawCommand(`ADD 1 DECKLINK ${deviceId}`);
}
```

**Issues**:
1. **No idempotency guard**: Calling `startDeckLink` twice adds duplicate DeckLink consumers, potentially crashing CasparCG. Add `REMOVE` before `ADD`, or check if device is already active.
2. **Hardcoded channel**: Always channel 1. Works for single-channel setups but should at minimum be configurable.
3. **Missing DeckLink parameters**: `ADD` without `EMBEDDED_AUDIO`, `KEYER`, `LATENCY`, `BUFFER_DEPTH` uses Caspar defaults. Configurator should set these explicitly.
4. **`stopDeckLink` doesn't verify removal**: Should read back `INFO 1` to confirm DeckLink was removed.

### 2.3 `caspar.ts` — Live Routing Review

**Current implementation** (`caspar.ts:469-473`):

```ts
const buildLiveCommand = (preferredSource?: string) => {
    const source = (preferredSource || getSettingsSnapshot().liveInputSourceName || '').trim();
    if (!source || source === 'SOTA_Live') return '';
    return source ? `PLAY ${PROGRAM_CHANNEL}-${LIVE_LAYER} ${source}` : '';
};
```

**Issues**:
1. **Magical `SOTA_Live` gate**: If source equals `SOTA_Live`, returns empty string. This is an OBS-ism leaking into Caspar mode.
2. **No source validation**: If user types `decklink://device/99`, CasparCG errors silently.
3. **Layer 20 is hardcoded for live**: Should verify layer 20 is available before playing.

**Recommended fixes**:
- Remove `SOTA_Live` special case from Caspar path
- Validate DeckLink device numbers (1–8)
- Add `CLEAR 1-20` before playing live source to ensure clean state

### 2.4 `caspar_config.rs` — Config Write Safety

**Issue**: `write_config_file` does no atomic write. If CasparCG crashes mid-write, config file may be truncated/corrupted.

**Recommended fix**: Write to `.tmp`, rename atomically (the way Rust's `tempfile` crate handles it):
```rust
fn write_config_file(path: &Path, contents: String) -> Result<(), String> {
    let tmp = path.with_extension("config.tmp");
    std::fs::write(&tmp, &contents).map_err(...)?;
    std::fs::rename(&tmp, path).map_err(...)?;
    Ok(())
}
```
On Windows, `std::fs::rename` is not atomic (it replaces destination), but `MoveFileEx` with `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH` is. We use `std::fs::rename` as a reasonable approximation.

### 2.5 App-level State Machine Review

The playout service should have clearly defined states and transitions:

| State | Allowed Transitions |
|---|---|
| `DISCONNECTED` | → `CONNECTING` |
| `CONNECTING` | → `CONNECTED`, `DISCONNECTED` |
| `CONNECTED` | → `PLAYING`, `CUED`, `DISCONNECTED` |
| `CUED` | → `PLAYING`, `DISCONNECTED` |
| `PLAYING` | → `PAUSED`, `CONNECTED` (stop), `DISCONNECTED` |
| `PAUSED` | → `PLAYING`, `CONNECTED` (stop) |

**Current code**: No formal state machine, just boolean flags (`isCasparConnected`, `isCasparPlaying`). These can get into inconsistent states.

**Recommendation**: Add explicit state enum and guard transitions with `console.warn` + no-op on invalid transitions.

### 2.6 Performance / Efficiency

- **Clock interval** (`caspar.ts:214-218`): 100ms clock tick is fine for 25fps (~2.5 frames precision). Acceptable.
- **OSC listener buffer** (`caspar.rs:282`): 4096 bytes, fine for UDP OSC packets.
- **Duration parsing** (`caspar.ts:268-314`): Multiple regex matches per file. Could cache duration per path in a `Map`. OK for now given it only runs at play/cue time.
